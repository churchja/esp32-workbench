## What was built

An identify/backup/flash/restore workbench for ESP32-family boards, structured
around two ideas: knowledge persists in provenance-tagged profiles keyed by
eFuse MAC, and nothing writes to a board without a verified backup of *that*
board.

It started on PlatformIO, migrated to ESP-IDF v6.0.3 mid-session when the
official `espressif32` platform turned out unable to build Arduino for
C5/C6/H2/P4 at any version, and kept PlatformIO as a sibling rather than
deleting working capability.

All ten identified, backed up and hash-verified. Four were restored to their

**Read speed follows the USB interface, not the board.** Four USB-Serial/JTAG
boards from four vendors all cap at 230400 and all fail reproducibly at 460800;
two USB-OTG boards both reach 460800. Zero disagreement inside any group.

That claim is worth reading as a process story rather than a fact. It began as
"the ceiling is per-*board*", argued from three data points — and the fourth
board broke it, because the argument had conflated USB-OTG with USB-Serial/JTAG
as though "native USB" were one thing. Boards five, six and seven then *tested*
the corrected version rather than producing it, and it held each time. That is
the only claim this session that survived new evidence instead of being narrowed
by it.

It is still narrower than it sounds, and the README now says so: all four
agreeing USB-Serial/JTAG boards are ESP32-S3, so what is measured is that SoC's
USB peripheral, not the interface in general. A C3/C6/C5 would be the first real
test. Four confirmations from one silicon family is weaker evidence than four
across families, and the earlier wording did not distinguish them.

**Partition layout is a firmware decision recorded in hardware.** The M5 Stamp
carries M5Stack's stock dual 3.19MB OTA slots; the Stamp S3A running Bruce has a
single 4.875MB app and 3MB SPIFFS, having spent the OTA partner slot for a
larger image and filesystem — so it has no A/B rollback and must be reflashed
through the ROM bootloader. Reading the layout tells you what a board is *for*,
not merely what it is.

## A defect no silicon could have exposed

The table above is the case for connecting hardware. This one is the case for
the opposite: a bug that ran correctly on seven boards for the whole session.

`cmd_backup` wrapped the *entire* baud ladder in one timer and stored the result
as `read_seconds`. When a read failed at 460800 and succeeded at 230400, the
discarded attempt was charged to the rung that actually produced the image. The
number was never *wrong* — it was a valid upper bound. It was presented as a
measurement, and it inflated precisely the boards that fall back, which is five
of the seven here.

No check in the repo could catch it. Every backup succeeded, every hash
verified, every restore was byte-exact. The defect lived entirely in the
interpretation of a number that no test read and no tool consumed — which is
also why it took an adversarial reader rather than a failing run to surface the
second half of it.

The fix times each rung separately and returns them:

    [{"baud": 460800, "seconds": 5.3,   "ok": False},
     {"baud": 230400, "seconds": 751.2, "ok": True}]

Manifests gained `read_seconds` (the successful rung alone), `ladder_seconds`
(wall total), and `attempts`. Rounding happens at record time so that
`ladder_seconds == sum(rungs)` holds *exactly* rather than to within float error
— both numbers are published side by side, and a table whose figures do not add
up teaches a reader to distrust the rest of it.

Two things arrived with the fix that were not in the diagnosis:

- **The clock is `time.monotonic`, not `time.time`.** These are durations. A
  12-minute read is a wide enough window for an NTP correction to land inside
  it, and a wall clock can step backwards — producing a negative duration that
  no assertion in the repo would have caught. `usbwatch.py`'s `--timeout`
  compared two `time.time()` readings for the same reason and got the same fix.
- **The clock is injectable.** This is what made the change testable at all.
  With real time the scripted durations round to 0.0, `read_seconds` and
  `ladder_seconds` are trivially equal, and a test would pass against the bug.

The eight pre-change manifest entries were **not** retro-fitted; the split
cannot be recovered after the fact. Absence of an `attempts` key marks them, and
a test asserts no new entry can be written without one.

## What an adversarial review found that reading did not

The fix was reviewed by five independent lenses — control flow, data semantics,
test quality, API contract, documentation accuracy — each finding then handed to
a separate agent whose only job was to *refute* it. Twenty-eight agents; six
findings survived, all real — two in the code and tests, four in the prose.
Every one of them was in work that had already passed the full suite and the
smoke run.

**The manifest write had no test.** The reviewer did not merely assert this; it
proved it — copied the tree, reinstated the whole-ladder value at the one line where it
becomes observable, ran the suite — 42 PASS, 0 FAIL. Every new assertion stopped
at the *function's return value*; the three manifest keys that were the entire
deliverable were asserted by nothing. Nine assertions now drive `cmd_backup` end
to end, and that mutation fails two of them.

**One assertion could not fail.** `a0 == round(sum([a0]), 1)` over a list
already asserted to hold one element. It inflated the headline count without
adding discrimination. Replaced with one that pins rounding-at-record-time,
which nothing had covered.

**Two claims were wrong in opposite directions.** First: "the inflation hit
every USB-Serial/JTAG board" — the CH340 bridge board fell back too, so the set
was wrong. Correcting that, the replacement over-corrected to "every figure is
an upper bound" — also wrong, because the S3's 731s was a *pinned* 115200 read
and the S2's 33s took the first rung. Both are clean measurements. Only two of
the four cited figures are inflated. The second error is the more instructive
one: being shown a claim is too narrow is not evidence that the widest available
claim is right.

## Four recurring failure patterns

These repeated often enough to be worth naming. All four are mine.

### 1. Checks that report success for the wrong reason

Nine instances:

- `command -v -a` is invalid in `/bin/sh`; `|| true` ate the error and the check
  reported "single esptool install" while three existed
- `git check-ignore -q` reported a file ignored while the dry-run showed it
  staged
- `usbwatch --wait --all` exited 0 instantly, because macOS always has non-USB
  serial ports
- `--wait` then exited 0 again, because a board was *already* attached — I had
  patched the trigger I observed instead of asking what `--wait` meant
- `idf-gate:integrity` asserted the *presence* of a bug I had just fixed
- the suite reported 42 passing with the original timer bug reinstated — no
  assertion read the manifest, so "green" meant "nothing looked"
- a partition-table comparison hashed one side with a hand-rolled md5 over the
  `0xff`-stripped region and compared it against the profile's
  `partition_table_md5`, which is the md5 record **ESP-IDF embeds in the table**
  (magic `EBEB`, covering only the real entries). Two different computations over
  two different byte ranges, reported as an equality test. Confirmed afterwards:
  the hand-rolled method returns `cc9a39b7…` where the tool reports `67654859…`
  for the same bytes. The conclusion happened to be right, having been re-derived
  by parsing both tables — so the bad check cost nothing except the confidence it
  was never entitled to lend
- a mutation sweep counted `FAIL` lines and reported **0 failures** for two
  mutants that had in fact crashed on an exhausted fake clock. A crash prints no
  `FAIL` line and aborts every assertion after it. `smoke.sh` checks the exit
  code and would have caught them, but the sweep I was reading did not — so I
  came within one step of recording a coverage hole that did not exist

A tenth instance cost a published claim **twice**, and is the sharpest one here.
Three port losses on an S2 were attributed to `--after no-reset` and written into
the README and a profile as a `verified` mechanism. The observation could not
distinguish *"no-reset caused this"* from *"hard-reset caused this"* — the port
was simply gone either way — and the code turned out to be discarding the option,
so three of the four operations never ran with the setting they were credited to.

The retraction that followed was **also** wrong. It established that the one
clean operation had parked successfully, concluded parking was fine, and stopped
— replacing an unverified claim with a different unverified claim.

Measuring it settled it: the CDC endpoint re-enumerates for under a second after
every esptool call, so back-to-back commands race. Absent at 0.5s, present from
1.0s, stable to 10s. `--after no-reset` parks an S2 correctly.

**And the README had already recorded that**, in the defects the QT Py exposed:
*"back-to-back esptool calls contended for the USB CDC endpoint."* Same chip
family, same mechanism, two hundred lines above the section where a new one was
invented. A symptom with an existing explanation in the same document was given
a fresh one — and the fresh mechanism was independently true, which is exactly
what made it comfortable enough to publish twice.

An eleventh instance had no code in it at all. Having reset a board and *verified*
it with a behavioural probe, I then wrote "the M5 Stamp is parked in download
mode" in four consecutive summaries — carrying forward a claim that my own
earlier output had already disproved. Restating is cheaper than re-measuring,
and nothing checks prose.

The shape is always the same: a status signal that collapses **"I couldn't
look"** into **"I looked and found nothing."** The fix is never "be more
careful" — it is writing the check so its broken state is distinguishable from
its passing state, and cross-checking against a second independent source.
Where no check exists, as in a summary, the discipline is to consult the
evidence already produced rather than repeat the last thing said.

The mutation-sweep instance sharpens that: the tooling *reporting* on the checks
needs the same property as the checks. Two fixes followed. `usbwatch`'s fake
clock now raises a named error that the harness converts into a reported value,
so a loop that never trips its deadline reads as `never tripped the deadline`
rather than a traceback; and the manifest assertions in `test_flash.py` read
through `.get("attempts", [])`, so a missing key is one reported failure instead
of a `KeyError` that takes out every assertion after it.

### 2. Generalizing from one specimen

Five instances: the S3's secondary console assumed to cover the S2; native-USB
port churn assumed to cover bridge boards; ESP32-family eFuse fields assumed
universal until an ESP8266 reported none; a "per-board" baud ceiling argued from
three boards that a fourth reorganised into per-*interface*; and "the timer bug
inflated every USB-Serial/JTAG board", generalised from the four boards in front
of me while the CH340 bridge — which also fell back — sat outside the set.

The tell is that the tidy explanation always fits the data in hand. Corrected
versions are consistently weaker and more useful — *"NVS is written on boot, the
byte count is device-specific"* rather than *"tinyuf2 writes the same keys."*

The worst instance was writing one into the README **as the justification for a
design**. Code gets tested; a stated rationale just gets believed.

The correction to the fifth instance produced its own failure worth naming
separately: told the set was too narrow, I replaced it with the widest available
claim ("every figure is an upper bound") rather than the correct one. Two of the
four figures were clean. Being shown a boundary is in the wrong place says
nothing about which direction to move it.

### 3. Fixing where the symptom is, not where the pattern is

One instance, found by measurement rather than review. `--after` defaults to
`hard-reset` in esptool, which caused two documented failures and was fixed in
`backup`. It was still live in `restore`, `flash` and `erase` -- every other
write path -- because the fix landed where the symptom had appeared.

It surfaced only because a restore verification asked for `--after no-reset`,
got a hard reset anyway, and 65 bytes appeared in a board's `nvs` that should
not have moved. The option was parsed, accepted and discarded. Nothing failed;
the wrong thing happened quietly and looked like firmware behaviour.

The tell is a fix whose scope is defined by the bug report rather than by the
code. The question the earlier fix did not ask is *where else does this call
shape appear?* -- one grep, five months earlier.

### 4. Tests that assert the environment

`test_idf_gate.py` accumulated three assertions that were true when written and
false later: no board attached, then a board with a backup, then one without.
Each described *the room* rather than the code's decision. A comment now names
all three so a fourth is not added.

## Seven restores, and what made each one mean something

`restore` is verified by reading the flash back and comparing **region by
region**, never by a whole-image hash. A hash answers "same or not", which is
the wrong question: `nvs` moving means the firmware booted and did its job,
while one byte moving in an app slot means the restore failed.

| Board | Image | `nvs` delta | Every other region |
|---|---|---|---|
| ESP8266 | 4MB | 0 | identical |
| QT Py A ×2 | 4MB | 50, 50 | identical |
| QT Py B | 4MB | **49** | identical |
| LilyGo | **16MB** | 0 | identical |
| Flipper module | 4MB | 0 | identical |
| Satellite1 | **16MB** | 65 | identical |

The interesting question is not the deltas but **what made each test capable of
failing**, because two of them nearly were not:

- The **LilyGo** had different firmware flashed onto it and restored, so a match
  meant something. But the verification came hours and several power cycles
  later, so a non-zero `nvs` delta could not have been attributed to the restore.
  The zero result made the caveat moot; it is recorded anyway, because it was
  correct for the result it was written against.
- The **Flipper module** was bit-identical to a backup taken six hours earlier —
  its firmware writes nothing to flash. Restoring bytes already present and
  finding a match is indistinguishable from the write doing nothing, so the chip
  was **erased first** and confirmed blank (0 of 131,072 bytes non-`0xff`) before
  restoring. That step is the difference between a verification and a tautology.
- The **Satellite1** needed no such trick: v0.2.0 had been flashed onto it hours
  earlier, so the flash genuinely differed. Its 65-byte `nvs` delta turned out
  to be a **bug's fingerprint** rather than firmware behaviour — see below.

The comparison itself became `tools/cmpflash.py`, after being written ad hoc
five times. It exits 0 for bit-identical, 1 for writable-region-only, 2 for a
region that must match, 3 for cannot-compare — encoding the distinction rather
than leaving it to the reader. Writing its tests immediately found a defect: a
partition declaring more space than the image holds made the regions tile past
the end, reporting sizes for bytes never read. Regions are clamped now and the
anomaly is named.

## Firmware updated on two boards, and what verified it

Both updates were real work the operator wanted kept, not tests to be reverted.

**The Satellite1** went from `v0.0.5-beta.1` (ESPHome 2024.11.2, IDF 4.4.8) to
**v0.2.0** (ESPHome 2026.4.5, IDF 5.5.4) — about thirteen releases. A vendor
factory image is not a restore: it carries its **own partition table**, and
writing one that disagrees with the board silently strands whatever lived in the
old layout. Three checks before writing — parse the image's table and compare it
entry-by-entry against the probed one, confirm the image's byte span does not
reach `nvs`, confirm the gate has a verified backup — then re-probe rather than
trusting "Flash complete".

**The LilyGo** got LilyGO's published factory image, which is not on the
Releases page at all: every release carries zero assets and the firmware lives
in the git tree at `firmware/firmware.bin`.

### The one field in `esp_app_desc_t` that identifies a build

The LilyGo flash could not be verified by anything readable. The published image
and the one it replaced carry **byte-identical** descriptors — same project, same
version string, same build date **to the second** — while differing in 70.7% of
their bytes. Only `app_elf_sha256` moved.

That field failed four distinct ways in one session:

| failure | evidence |
|---|---|
| does not identify a **board** | LilyGo and M5Stack Capsule stamps collide byte-for-byte |
| does not identify a **build** | two different binaries share it exactly |
| cannot separate two builds of one project on one board | the LilyGo flash |
| does not **date** the firmware | it is the arduino-lib-builder core's timestamp, not the sketch's |

`app_elf_sha256` covers the first three. Nothing in the descriptor covers the
fourth — there is no reliable way to date an Arduino-built ESP32 firmware from
the chip alone.

Comparing *symbol strings* between the two binaries answered what the LilyGo
flash actually gained, with no source to diff: the published image references
**PCF85063** twice and the resident app **not at all**. The board has that RTC at
`0x51` — it is one of the three devices that identified it as the Plus — and the
firmware it shipped with could not talk to it.

### Resolving a variant by measurement rather than reading

"LilyGo T-Display S3 AMOLED" is a family of at least six boards, all
ESP32-S3R8 with 16MB flash and 8MB PSRAM, so the eFuse reading that separated
every other board here separated nothing. Neither did the partition table
(stock `arduino-esp32`), the USB ID (generic Espressif) or the app stamp.

Five research lanes concluded the variant was undeterminable and recommended
looking at the panel. That was wrong: LilyGO's own library **autodetects by I2C
probe**, and running it settled the question in seconds — CST816 touch, a
PCF85063 RTC and a BQ25896 PMU on one bus is the 1.91in **Plus** and nothing else
in the family.

The result then indicted every guess that preceded it. All three conflicting
GPIOs resolved to the side that would have been wrong, and the circumstantial
evidence — a board JSON matching flash size, mode, memory type, hwids *and*
partition file — pointed at a **sibling**. Four matching fields is not
identification when the fields are shared across a product line.

## What a USB-OTG port actually does

Worth stating plainly, because three sections of this log describe getting it
wrong and none state the result:

On a USB-OTG part (ESP32-S2), **the CDC endpoint re-enumerates for under a
second after every esptool operation, then returns and stays.** Polled at 0.5s
intervals after a command: absent at 0.5s, present from 1.0s through 10.0s.

| | USB-Serial/JTAG (S3, C3, C6, C5, H2, P4) | USB-OTG (S2) |
|---|---|---|
| What provides USB | hardware peripheral, independent of firmware | firmware, or the esptool stub |
| `--after no-reset` | port persists | **port persists** — parks correctly |
| Back-to-back commands | fine | **race** — allow ~1s, or retry once |
| `--after hard-reset` into firmware that shows no USB | port persists | board goes invisible |
| After a whole-chip erase | port persists | nothing left to enumerate; needs BOOT+RESET |

The two rows that differ are not about parking. They are about whether anything
exists to bring USB up after a reset — which is the real USB-OTG property, and
the one that held across every wrong version of this claim.

## Practices that earned their keep

- **Read `--help`, don't recall flags.** esptool 5.x hyphenates every
  subcommand; every tutorial online uses the 4.x underscored form.
- **Verify against a second source.** Renaming `master` → `main` looked failed
  because `gh api` served a cached `default_branch`; the wire disagreed.
- **Mutation-test any check that passes.** Every profile reports `current`, so
  a classifier hardcoded to return `current` would look identical on real
  data. Promoted to routine by the timer work, where it stopped being a
  sanity check and became the evidence: ten mutants across the two fixes,
  each reported by how many assertions it breaks. It answers the one question
  a test suite cannot ask of itself — *would this catch the thing it exists to
  catch?* — and it is the only reason the untested manifest write was found.
- **Have something adversarial read the diff.** Five lenses over one change,
  each finding handed to a separate agent tasked with refuting it. Six survived
  and all six were real — two in the code and tests, four in the prose — in work
  that had already passed the full suite and the smoke run. Reviewing my own
  diff had found none of them, because I was checking it against the intent I
  already held.
- **Publish the negative result.** More of this session's value is in what
  could *not* be determined than in what could: a board family the probe cannot
  discriminate, a build stamp that identifies nothing, a claim retracted after
  its evidence turned out to measure something else. Each is recorded as a fact
  with provenance rather than left as an open question the next session reopens
  from scratch.
- **Generate documentation from data.** The tables built from `boards/*.yaml`
  stayed correct; the hand-maintained Layout table drifted through a framework
  migration, three new tools and a 150-assertion increase before an audit caught
  four defects at once. `tools/test_docs.py` closes that.

## Still open

- **The EUI64 MAC path.** Only runs on C6/C5/H2, which none of these boards are.
  Recorded in the initial commit, in code comments, in a test asserting an
  8-byte address does not pass as a MAC, and in the README.
- **ESP8266 build support.** Identification, backup and restore work; building
  needs ESP8266_RTOS_SDK, not ESP-IDF, and none is claimed.
- **The LilyGo's board-level facts.** Display controller, pin map and battery
  divider ratio are all still `unknown` in its profile — none are probeable, and
  the divider in particular is a magic number that silently corrupts every
  reading if guessed. `esp-bsp` may already encode the panel.
- **Whether the baud ceiling is really per-interface.** Six agreeing
  USB-Serial/JTAG boards share one SoC family. Only a C3, C6 or C5 tests the
  claim as stated.
- ~~Whether `--after no-reset` is safe on a USB-OTG part.~~ **Answered by
  measurement**: it is. The port re-enumerates for under a second after every
  esptool call and returns — a race, not a loss. Allow ~1s between back-to-back
  commands on an S2, or retry once on "port is busy". See the tenth instance in
  pattern 1 for how two wrong answers were published before anyone measured it.
- **The XMOS co-processor on the Satellite1.** It has its own SPI flash that
  esptool cannot see, so a full backup does not contain it. Not unrecoverable —
  the ESPHome build embeds an image and reflashes on boot — but it means the
  backup guarantee is narrower on that board than on the other nine, and no
  tooling here reads or writes that chip.
- **The fallback cost is not a constant and has no model.** Four measurements:
  4.7s, 7.4s, 9.5s, 36s. The spread grew with every sample, which is the
  opposite of what a converging measurement does.
