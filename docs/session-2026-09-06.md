# Build log — 2026-09-06

A second application on the LilyGo T-Display S3 AMOLED Plus, and four
peripherals on that board that went from unknown to measured. Follows
`docs/session-2026-09-04.md`, which built the workbench itself.

Recorded because the *reasons* are more useful than the diff. Almost everything
worth writing down here is a case where something that looked verified was not.

## What was built

`projects/lilygo-vaultweather` — a Fallout-styled clock and weather station.
24-hour clock, current conditions merged per-field from a personal weather
station and Open-Meteo, a 3-day forecast, animated condition icons, tap-to-wake
on the touch panel, and a battery-backed clock that survives a power cut.

Setup is a SoftAP captive portal, so no Wi-Fi credential ever enters the source
tree. The board is configured by joining `VAULT-TEC-SETUP` from a phone.

Also `projects/lilygo-pipboy`'s detonation animation, replaced with
pre-rendered frame art.

## The bug that hid behind three reviews

`wx_ui.c` opens with an eighty-line layout arithmetic block: every element's
right edge computed and compared against the 536px panel. Three separate passes
read it. All three missed that its central premise was wrong.

The block asserted "a string of N characters is exactly 8*N pixels wide" for
`lv_font_unscii_16`. Every glyph in that font has `.adv_w = 256`, and LVGL
stores advance width in 1/16-pixel units, so the real figure is **16 px per
character**. The font is `unscii-8.ttf` rendered at `--size 16`, which doubles
it. `lv_font_unscii_8` genuinely is 8 px, which is exactly the kind of partial
truth that makes a wrong generalisation feel checked.

Every character budget in the file was off by 2x. The visible symptom was a
72px label holding `"SYNC 0M"` — 112px — which LVGL word-wrapped, dropping its
second line on top of the row beneath. It was reported as "there is an icon or
some graphic behind the SYNC PWS", and guessed at as a connection indicator.

A worse instance had not been seen yet: the CURRENT+ panel's right column
starts at x280 with a 22-character budget. At 16px that is 352px, running to
x632 on a 530px pane. It only ever showed while the panel was rotated away.

**What broke the deadlock was not more reading.** `lv_snapshot_take()` renders
the live object tree into a buffer; dumping that over serial and decoding it on
a host produced a picture, and measuring "SYNC" at ~60px for four characters
settled it in one step. Re-reading arithmetic only re-confirms the assumption
the arithmetic was built on. `adv_w = 256` lives in a generated font file that
nobody thinks to open.

The capture path is now permanent: `tools/screenshot.py`, triggered by a
keystroke over the serial console.

## Things that were true, and stopped being true

Two defects this session had the same shape: a proxy that was valid when it was
written, invalidated by a later change, with nothing to notice.

**`wx_time_sync()` decided success by asking "is the year past 2024?".** That
was a sound proxy for "SNTP has synced" for exactly as long as SNTP was the only
thing that could set the clock. Adding a battery-backed RTC that restores the
clock *before* the network comes up made it plausible in advance, so the wait
loop returned on its first check, logged `clock set` for a time SNTP never
supplied, and the caller wrote the RTC back with its own value — a no-op. SNTP
corrected the system clock a second later and the RTC was left behind.

The whole visible evidence was a **two-second** number on a console command. A
crystal does not drift two seconds in five minutes, so it had to be a symptom.
Fixed by tracking `esp_sntp_config_t.sync_cb` — set *before*
`esp_netif_sntp_init()`, because the wrapper installs its own notification
callback unconditionally and chains to it. Success now requires both a sync
event and a plausible year: the callback proves SNTP delivered something, the
year proves it is not garbage, and each alone has now been wrong here.

**The brightness schedule compared minutes-of-day.** Fine, until the clock could
start in UTC — the POSIX TZ only arrives with a forecast and the NVS cache
stores none. With cached sunrise 11:59Z and sunset 00:47Z the test becomes
`mins >= 719 && mins < 47`, false for all 1440 minutes of the day. The panel
would have gone dim at noon on every cold boot, recovering only on the next
successful fetch — so never, with the router down. An impossible window now
fails bright, which also makes the two "we do not know the time" states agree
instead of resolving to opposite extremes.

## A gate that could not fail

Worth recording as a process defect rather than a code one. A board profile
edit introduced `SNTP's` inside a single-quoted YAML scalar, where an
apostrophe must be doubled. `tools/validate_profiles.py` caught it immediately
and the commit landed anyway, because the shell chained validator to commit
with `;` instead of `&&`.

A check that runs, reports, and is structurally incapable of blocking is worse
than no check: it produces the appearance of verification. The failure mode is
not "the gate was skipped" but "the gate was consulted and overruled by
punctuation".

Blast radius was small only by luck of the failure class — a YAML parse error
fails loudly for every consumer, so nothing downstream absorbed a wrong value.
A subtly wrong *value* would have propagated silently.

## An address ACK is not a working chip

`boards/e4b0638aec2c.yaml` recorded, from a September 4 scan, that 0x15, 0x51
and 0x6B answer on SDA=3/SCL=2. That identified the board variant and was
genuinely useful. It also proved less than it appeared to.

An ACK proves a chip is powered and decoding its address. It says nothing about
whether the register interface behaves. This session read registers:

| Part | Was | Now | What the read added |
|---|---|---|---|
| CST816 touch | ACK at 0x15 | chip id `0xB5` | it is a CST816**S**, and registers work |
| PCF85063 RTC | ACK at 0x51 | read + written | time survives a power cut, to ±0.5s |
| BQ25896 PMU | ACK at 0x6B | still ACK only | left at `probed`, honestly |

The touch controller had ACKed for two days before anyone read a register off
it. The vendor's own header comments that entry `"Touch CST816T"` — 0xB6. The
silicon says 0xB5. A register read outranks a source comment.

`peripherals.rtc` and `peripherals.charger_pmu` therefore sit at different
provenance levels on purpose. The ladder exists to make that distinction
expressible.

## What the schematic settled that probing could not

Fetching `T-Display-S3-AMOLED-Plus.pdf` (V1.0, 2024-10-21) closed three open
questions at once:

- **The touch controller has no reset line.** The FPC is six pins — SCL, SDA,
  INT — and LilyGO's board struct records `{3 SDA, 2 SCL, 21 IRQ, -1 RST}`. The
  driver had carried a comment guessing GPIO17 might be shared. There is
  nothing to share, which is why the CST816 sleep hazard never materialised.
- **A second PMIC exists and is invisible to a bus scan.** The AXPM65611 (U4)
  generates the AMOLED rails and is SWIRE/EN controlled, not I2C — which is why
  a scan finds three devices on a board carrying two power ICs. Its enable is
  GPIO38, the pin already recorded as `lcd_pwr`. "Display power" on this board
  is really "AMOLED rail PMIC enable", which explains why getting its polarity
  wrong killed the panel outright rather than dimming it.
- **There is no audio hardware.** Recorded as an explicit absence, with the
  complete U1–U8 inventory, so the question is not asked a third time.

## Measuring the thing rather than a proxy for it

The RTC offset was reported as an integer difference of two whole-second values.
It flipped between −1 and +1 on a perfectly good clock, because both sides are
truncated — it measured quantization, not drift.

Subtracting the system clock *with* its microseconds gives the real offset, and
with that instrument a design question resolved cleanly:

| Write strategy | Measured offset |
|---|---|
| Round to nearest | +1.21 … +1.24 s |
| **Truncate** | +0.006 … +0.096 s |

Truncation looks like an off-by-one and is correct. The part does not reset
prescaler stages F0/F1 on a write (datasheet §7.2.1.2), so its first increment
lands 0.508 s early and it inherently starts half a second fast. Truncating
subtracts the half second the prescaler is about to add back.

±0.5 s is the floor — whole-second registers, no addressable prescaler phase —
and it is invisible on a display showing HH:MM. It is worth getting right only
because a baseline near zero is what makes genuine drift legible over months.

## Two datasheet traps obeyed rather than discovered

Both from NXP PCF85063A Rev 7.3, fetched rather than recalled. Either would have
produced intermittent, plausible-looking wrongness.

**Registers 04h–0Ah must be accessed in one transaction.** The part blocks its
counters for the duration, so a burst cannot tear — but a *split* access can
straddle a rollover and return the minutes from before it and the hours from
after. The datasheet says so explicitly; nothing in the API would stop you.

**The access must finish within one second.** Only one pending increment is
buffered while the counters are blocked, so a slow transaction makes the RTC
lose the excess silently, permanently, and only ever downward.

Also: the weekday register is plain binary, not BCD, and the chip never derives
or validates it against the date. And epoch conversion is hand-written rather
than `mktime()`, because `mktime` interprets its input in the *current*
timezone while this app changes TZ at runtime from the weather API — the clock
would have shifted by the UTC offset, and only after the first forecast
arrived, which would have looked like a network fault.

## Art that had to be looked at

Three frame-art generators were written this session: the detonation, the
weather icons, and the moon. Every one needed multiple passes, and every fault
was invisible until the frames were rendered and inspected.

The detonation took four. Its first version had a rectangular stem, an
elliptical ring and a flat crescent cap — three geometric shapes in a brief that
said no geometric shapes. The second overcorrected: wobble at 0.20 plus an
eighth harmonic swung the radius between 0.62r and 1.38r and every lobe became a
spiky maple leaf. The third drew a lightning bolt where the stem should be,
because its two edges oscillated six times over their length and crossed. The
fourth fixed a flat bottom edge that the ink outlined as a box across the base.

The moon needed a different kind of fix. Eight phase buckets are 3.7 days wide,
so a moon 1.7 days past last quarter — 32% lit, visibly a crescent — was
labelled `LAST QTR`. One index was doing two jobs at incompatible resolutions:
picking a 96×96 tile and naming a phase. Splitting them is what fixed it; more
buckets alone would have moved the error rather than removed it. The four
instant names (new, first quarter, full, last quarter) now hold a ±0.6-day
window and crescent/gibbous cover the rest.

**A1 is a trap on this stack.** `LV_COLOR_FORMAT_A1` is a valid enum in every
LVGL build, but in 9.5 the software renderer has no blitter for it — grep the
tree and A1 appears only under `src/draw/nema_gfx/` and `src/draw/vg_lite/`,
hardware accelerators the ESP32-S3 does not have. An A1 image compiles clean,
links clean, and draws nothing, with a runtime `LV_LOG_WARN` as the only trace.
All three generators emit I1, whose eight palette bytes are mandatory even
though the blend never reads them, because `lv_draw_buf_goto_xy()`
unconditionally skips them.

## Corrections to things stated earlier in this repo

- The claim that the vendored RM67162 driver leaves the panel at `0xD0`
  (208/255) is wrong: that branch is dead code. With
  `CONFIG_RM67162_USE_LILYGO_SPI_INIT` set, `panel_rm67162_init` returns early
  into LilyGO's table, which sends `LILYGO_DEFAULT_BRIGHTNESS = 175`. Driving
  the panel to full is a 46% gain, not 23%.
- `esp_http_client_config_t` has two buffer fields. `buffer_size` is receive;
  `buffer_size_tx` defaults to 512 and holds the whole request line. Open-Meteo's
  field-selection URL is 551 characters, so every forecast fetch failed with
  `Out of buffer` before a byte left the chip — which read as a parse bug,
  because the PWS tiers kept working and only the API-only fields went blank.
- ESP-IDF 6.0 removed both the bundled cJSON component and `wifi_provisioning`.
  The hand-rolled setup portal is not a preference.

## Where verification stopped

Stated so the next person does not mistake inference for measurement.

- **The OS oscillator-stop rejection path is unexercised.** It only fires once
  the RTC backup cell has actually failed, which cannot be staged without
  damaging the board.
- **The touch coordinate frame is unresolved.** Readings brush x=240 while y
  stays low, pointing at the panel's native 240×536 portrait frame, rotated 90°
  from the 536×240 the app draws in. Tap-to-wake does not care; anything mapping
  a touch to a UI element must establish the transform by tapping known corners.
- **The microSD slot has never been exercised.** Pins are `vendor_doc` from the
  schematic and LilyGO's header, not probed. GPIO11–14 are also broken out on
  the P4/P5 headers, so anything driving them fights the card slot.
- **`peripherals.charger_pmu` is `probed`, not `verified`.** 0x6B ACKs; no
  register has been read.
