# Build log — 2026-09-07

A dark screen that was not a fault, on a board that was not the one being
examined. Follows `docs/session-2026-09-06.md`.

Recorded because almost nothing here went the way it was framed, and the
corrections are the content. Four errors were published and retracted in public
during this session; each one is below with how it was caught.

## The wrong subject

The session opened with a working diagnosis: a board running ESP32 Marauder
v1.12.3, build target `MARAUDER_DEV_BOARD_PRO`, identified by exact SHA-256
against the release asset. That target has `//#define HAS_SCREEN` commented out.
The owner reported a dark screen. The conclusion wrote itself — wrong build,
flash the right one.

Everything in that chain was true and the conclusion was wrong.

The owner photographed the working screen. Its Device Info page reported Station
MAC `48:9D:31:02:A9:48`. The board on the bench read `48:9D:31:02:7E:98`. Both
are genuine Espressif OUI assignments, not randomised locally-administered
addresses. **Two physical chips.** "Double Barrel" is literal: two Marauder units
in one enclosure, and everything profiled belonged to the second one, which has
no panel, no SD and no GPS by design and had been reporting exactly that at every
boot.

Three true statements produced one false conclusion:

* the owner said there was a screen — true of the device
* the vendor documented a 2.8-inch touch screen — true of the device
* this chip reported no display — true of the chip

They fused through an unexamined assumption that the enclosure held one ESP32.
The product name contradicts that assumption and was read past for two days.

Retracted as a result: `display.present`, `display.panel_type`,
`display.controller`, the entire `pinmap`, `hardware_target: MARAUDER_V6`, a
"three faults, one cause" symptom set, and a recommendation to flash `_v6.bin`
that would have put a screen build onto a screenless unit.

## Verification cannot tell you the claim is about the wrong thing

Every check made against the wrong board did its job. Two full backups. A
region-by-region `verify-flash` read-back against the silicon — bootloader,
partition table, otadata, app0, app1, spiffs all digest-matched. An exact SHA-256
firmware identification. A MAC-keyed backup gate.

All correct. All pointed at the wrong subject. The one artifact that would have
caught it was a MAC, and it was on screen the moment the owner photographed it.

## A negative that cost seven attempts

The screen unit could not be reached over USB. Recorded as a matrix so it is not
repeated:

    left USB-C, plain connect ........ MAC ...7E:98 (the other unit)
    top USB-C, plain connect ......... no USB device at all
    left-edge switch flip ............ no port change, MAC unchanged
    both dots, paperclip on insert ... nothing new
    dot 1 + cold power-cycle + loop .. CONNECTED attempt 3/20 -> ...7E:98
    dot 2 + loop ..................... 9/9 boot mode 0x13
    dot 2 + cold power-cycle + loop .. 16/16 boot mode 0x13

The deciding observation was `0x13` itself, and it is stronger than a timeout
would have been. `esptool` does not infer that number, it **reads a boot message
off the UART**. Something announced `SPI_FAST_FLASH_BOOT` on that wire on all 25
attempts, and that something is the second unit. A wire carrying the second
unit's boot banner is the second unit's wire.

Two things learned along the way that cost real time:

**The battery defeats the boot button.** GPIO0 is sampled once, on the rising
edge of reset. A board with an onboard battery does not lose power when USB is
unplugged, so no edge is generated and the boot button does nothing at all.
Several "the boot button had no effect" results were really "no reset ever
happened".

**Two connectors, different reset wiring.** The micro-USB has full auto-reset;
the left USB-C has EN but not DTR→GPIO0, so `esptool` returns "Wrong boot mode
detected (0x13)" unless the button is held. A board that suddenly cannot be
auto-reset after dozens of clean connections looks like evidence of a different
*chip*. It was a different *connector*.

**Method worth reusing:** holding a boot button and connecting asks the human to
hit a window they cannot see. Retrying `esptool` every ~5s for 90s while they
simply keep the button down removes the timing problem entirely.

## Advice given twice before looking

The SD card was recommended, twice, as "the backup worth taking — settings,
captures, portal assets, the part no release asset can replace". Then it was
mounted. It contained one empty directory. The ~2MB `diskutil` reported as used
was `.Spotlight-V100` and `.fseventsd`, written by macOS at insertion.

Everything about the contents had been inferred from what a Marauder SD card
usually holds, never from this one. It cost ten seconds to check.

Also worth knowing, given how careful the rest of this repo is about not writing
to things: **macOS writes to removable media on mount, unprompted.** A forensic
image of a card has to be taken before macOS ever sees it.

## An upstream bug, and three wrong things said about it in public

Upgrading the screen unit v1.12.1 → v1.15.1 cost it the battery meter.
Root-caused to PR #1392 ("Fix v7 battery and wardriving", merged 2026-07-20),
which flipped V4/V6/V6_1/KIT alongside V7:

    -      #define HAS_IP5306
    +      #define HAS_MAX1704X
    +      #undef HAS_IP5306

The regression is not visible in a diff of the two endpoint configs.
`HAS_IP5306` is undefined in **both** v1.12.1 and v1.15.1. It exists only in the
interaction: v1.12.3 added `#ifdef` guards while the macro was defined
(harmless), then v1.14.0 withdrew the macro and left the guards.

Reported on issue #1477, which had sat open and undiagnosed since 2026-08-17.
Then corrected, twice:

1. **The suggested fix was wrong.** "Define both `HAS_IP5306` and
   `HAS_MAX1704X`" collapses to IP5306 only, because a cleanup ladder at
   configs.h ~2931 does `#elif defined(HAS_IP5306)` → `#undef HAS_MAX1704X`. It
   would have fixed IP5306 boards by breaking MAX17048 ones. Retracted publicly.
2. **`BatteryInterface::begin()` does not exist.** The method is `RunSetup()`,
   at both tags. Asserted twice, after an earlier grep for `begin()` returned
   nothing and that silence went unnoticed.

## The control build

Neither correction came from re-reading. Both came from running things.

The fix is one line. Building it proves nothing on its own — of course it
compiles. So the **unpatched** source was built first, with the same toolchain,
and compared against the published binary:

    official esp32_marauder_v1_15_1_20260824_v6_1.bin   1,710,224 bytes
    unpatched control build                             1,711,408 bytes  (+0.07%)

Identical `app_desc` fields, both structurally valid. That is what made the
patched build trustworthy.

It also caught the `#undef HAS_MAX1704X` trap: **the patched binary came out
2,048 bytes smaller than the control**, when adding a code path should grow it.
That anomaly was the only reason to look. Confirmed by string count rather than
by re-reading the source that had already misled once:

                        "Detected IP5306"   "Detected MAX17048"
    official                    0                   1
    stock control               0                   1
    patched                     1                   0

Two CI steps poison the build silently if skipped, both required for core 3.3.4:
`platform.txt` gains `-Wl,-zmuldefs`, and every `cpp_flags` under
`esp32-arduino-libs` needs `-fexceptions` → `-fno-exceptions`.

## Two predictions, made from source, confirmed on hardware

The fix was flashed via the SD updater — the only route this unit has.

**The meter reads 50%, a quarter value.** The IP5306 path returns only
25/50/75/100 because it maps two register bits. A MAX17048's float
`cellPercent()` would essentially never land on a round quarter. So the number is
evidence of *which probe answered*, not merely that battery code runs. Read
backwards, it also explains the owner's original v1.12.1 screenshot of 75%.

**The status-bar percentage returned**, and that symptom was never observed
broken. It was derived from `i2c_supported` having exactly two consumers,
`WiFiScan.cpp` and `MenuFunctions.cpp`. Predicting a symptom you have not seen
and watching it resolve tests the model harder than fixing the one you were
handed.

## The PR, and a guard defeated three different ways

Submitted as https://github.com/justcallmekoko/ESP32Marauder/pull/1534 — one file,
+9 -1, against upstream master `91724fd`.

The split needed no judgement call in the end. `MARAUDER_V4` declares
`HAS_IP5306` in its own board block at `configs.h:257`, V6 and V6.1 at `:278`,
and KIT, V7 and V7_1 declare no IC at all. So V4/V6/V6.1 keep what they already
name and KIT keeps what it has today. Preprocessor-verified: only those three
targets change, and V7/V7_1 are byte-identical, so #1392's fix is preserved.

**The first attempt at that commit contained 616 files and 1,764,920 deletions.**
A `git stash` / `stash pop` around a failed `gh repo fork` had emptied the index.
It survived a `&&` chain because a **pipeline's exit status is its last
command** — `gh repo fork` failed with a bad flag, `| tail -2` succeeded, and the
chain continued.

That is the third variant of one bug in this repo's history:

    2026-09-06   `;` instead of `&&` -- validator failed, commit ran anyway
    2026-09-07   commit on the line AFTER the guard rather than behind it
    2026-09-07   guard defeated by a pipe swallowing the exit code

The lesson keeps being written one notch too narrowly. The general form is that
**an exit code nobody checked is not a guard**, and newlines, semicolons and
pipes each discard one. What actually caught it was printing `git show --stat`
and reading the number. The final version asserts the changed-file count is
exactly 1 and aborts otherwise.

Also corrected before submission: the PR body claimed the change was built and
run on hardware. The PR build and the flashed build are the same size,
1,709,360 bytes, but different hashes — master is ahead of the v1.15.1 tag the
device was running. The body now says the *fix* is hardware-confirmed and this
commit's binary is not.

## The audit that found nothing, which is a result

Asked what else the upgrade cost. Answer: nothing. Established two ways, both
reproduced locally rather than trusted:

1. Resolved `configs.h` with the real preprocessor at both tags
   (`gcc -E -dM -x c++ -DMARAUDER_V6_1`) and diffed the final macro sets. Only
   `MARAUDER_VERSION` differs. This has to be done with a preprocessor, not by
   reading: configs.h declares macros in board blocks and revokes them 2,500
   lines later, which is the exact trap the whole bug lives in.
2. Reachability diff across all 42 common source files. One file hit.

Patch variants were then measured rather than assumed:

    variant                        V6_1      KIT                       V4
    stock v1.15.1                  MAX1704X  MAX1704X                  MAX1704X
    ours (add define, drop undef)  IP5306    IP5306                    IP5306
    delete both lines              IP5306    AXP192+IP5306+MAX1704X    IP5306

The delete variant drops KIT to the `#else // punt` fallback with three drivers
at once. Ours is correct for this board and **not** a safe upstream patch, since
it flips KIT and V4 too. That was said plainly upstream rather than offering a
patch that fixes one board by breaking two.

## A guard nobody runs

PR #1326 (v1.13.0) was an earlier fix for this same bug and shipped a regression
guard, `tools/check_battery_driver_macros.ps1`. Nothing in the tree references
it — no workflow, Makefile or hook. The same bug returned one release later.

That is a sharper version of this repo's existing note on mutation-testing: a
check that has never been *run* is worth less than one that has never *failed*.

## A thirteenth board that cannot be backed up

`backups/` now holds 13 directories against 12 profiles. The extra is
`489d3102a948`, the screen unit. It has no USB data path, so no flash image of it
can be taken by any means available here.

The gate is keyed by eFuse MAC and behaved correctly throughout — it shows
nothing for that MAC and would refuse to flash it. It was never wrong; it was
never asked. A session spent protecting `...7E:98` gave its twin nothing, and the
twin is the unit carrying the user-visible firmware, the SD card and the battery.

What is held for it is an upstream release asset and a custom build, both clearly
labelled as *not* backups: app region only, never compared against silicon.

## Where verification stopped

The audit was static. No device was instrumented, and runtime behaviour, timing,
RF performance and memory pressure were not examined. The custom firmware is
confirmed working by its Device Info screen and nothing more.

The `489d3102a948` profile does not exist — that board has a backups directory
and a `sibling_board` section inside its twin's profile, which is a compromise,
not a design. It cannot be identified by `esp32ident.py` because it cannot be
reached.
